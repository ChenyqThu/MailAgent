## Key implementation decisions / learnings (for PR-4 / future sessions)

### 1. typer nested sub-typer for `calendar recurring discover/replay`
typer.add_typer can be nested — create a recurring_app = typer.Typer(name="recurring")
and `app.add_typer(recurring_app, name="recurring")` to get `mailagent calendar recurring <cmd>`.
This is documented but easy to miss.

### 2. CliContext shared between commands via typer.Context.obj
`notion resync` delegates to `email.email_resync(ctx, internal_id=..., ...)` — same typer.Context,
so CliContext.output / api_key / etc. all flow through. This avoids re-implementing the
resync logic in two places.

### 3. mock strategy for write commands
- LLMRunner: monkeypatch `__init__` to skip real client construction, then replace
  `run_for_internal_id` + `close` with async stubs. Pattern: `_patch_llm_runner` helper.
- NotionClient: replace the entire class with a StubClient that has `.client.pages` namespace.
  `_patch_notion_client(monkeypatch, pages_update=stub)`.
- AppleScriptArm: monkeypatch `__init__` lambda + `fetch_email_content_by_id` static func.
- NotionSync.create_email_page_from_sqlite: async fake returning CreateEmailFromSqliteResult.

### 4. AttachmentStore.read() path resolution
Default deployment uses base_dir=`MailAgent/data/attachments`, so `read("data/attachments/.../x.pdf")`
works via `base_dir.parent.parent / local_path`. **In tests** with `ATTACHMENT_STORAGE_DIR=tmp_path/attachments`,
the only safe choice is **absolute local_path** — relative resolution would land at `tmp_path.parent/...`
which is wrong. seeded_db_with_real_attachment fixture writes absolute path to email_attachment.local_path.

### 5. Auth caveat — env var doubles as both expected and provided
`src/cli/auth.py`: `provided = ctx.api_key or env.get("MAILAGENT_CLI_API_KEY", "")`. So setting
`MAILAGENT_CLI_API_KEY=expected-token` env actually satisfies BOTH expected and provided. To test
"auth-rejected with mismatched token" pass `--api-key wrong-token` as a flag override.

### 6. error wrapper schema consistency
All PR-3 commands' error JSON validates against `_common.schema.json` top-level oneOf
(wrapper_error branch). 11-case parametrize in test_pr2_followups.py:TestErrorWrapperConsistency
covers attach/llm/notion/calendar/email + 9 error codes.

### 7. NotionClient.__init__ side effects
`NotionClient.__init__()` constructs `AsyncClient(auth=config.notion_token)` — for tests
with empty NOTION_TOKEN this might error in real-network mode but not unit tests since
AsyncClient.__init__ is lazy about network. Still, prefer stubbing the whole class
(StubClient with `pages` namespace) rather than the inner client.

### 8. New error codes added (PR-3)
- E_LLM_FAILED (exit 1): runner ok=False, not a not-found case (gateway 5xx / parse fail)
- E_NOT_IMPLEMENTED (exit 2): command exists but PR-3 only ships stub
  (llm compare-paths non-dry-run; calendar expand non-dry-run; attachment derive non-dry-run)

### 9. Schema validation registry pattern (carried from PR-2)
referencing.Registry().with_resource(uri="_common.schema.json", resource=...) → jsonschema.validate
can resolve `$ref: _common.schema.json#/$defs/error`. PR-3 follow-up tightens dev extras to
jsonschema>=4.18 + referencing>=0.30 so install-from-clean has correct deps.

### 10. PR-3 stubs needing real implementation in PR-4
- `attachment derive` non-dry-run → `backfill derivatives` (PR-4)
- `llm compare-paths` non-dry-run → real two-path LLM comparison (currently scripts/compare_llm_path.py)

## 关键学习 (供 PR-6 / 未来 session)

### 1. 工作流分工严格执行有效
PR-4 时 Claude 自己写代码 + 让 codex review 是反模式: codex 容易认可自己后续要改的代码, 多轮振荡。
PR-5 改成 codex 写 + Claude 仅 review/commit, 出错率显著低; 一次 fix 通过率 ≥ 80%。
唯一翻车是 US-004 codex 只改了 admin.py, 没改 tests; 通过 SESSION_ID 继续同一 session 让 codex 补完。

### 2. codex_bridge.py + workspace-write sandbox 比 codex:codex-rescue 适合协作
官方 codex-rescue subagent 是为"救援"场景设计 (单次诊断 / 实现); 多 user story 顺序协作要用 collaborating-with-codex skill (memory: feedback_codex_collaboration_path.md)。
SESSION_ID 多轮也比起新 session 好 — codex 记得之前的工作上下文。

### 3. "保留 module 让 CLI import" 是合理选择
1846 行的 InitialSync 类 (scripts/initial_sync.py) 移动到 src/init/ 风险太大 (imports / tests / 流程依赖)。
PR-5 采用折中: 模块本身不动, CLI 直接 import, 仅在 __main__ block 加 DeprecationWarning。
后果: scripts/ 不能整体清空, 但破坏面最小。PR-6 (可选) 才做真迁移。

### 4. pyproject.toml ruff per-file ignore 给 .json
ruff 会把显式传给它的 .json 文件按 Python 解析 → `true` / `false` 报 F821 undefined name。
解决: pyproject.toml 加 `[tool.ruff.lint.per-file-ignores] "docs/cli-schema/*.json" = ["F821"]`。这是 US-005 codex 发现 + 加的。

### 5. mock 策略: monkeypatch 内部函数 > mock 整个类
US-006 + US-007 + US-009 都用 monkeypatch 替换内部函数 / 类 (e.g. `monkeypatch.setattr("src.cli.commands.notion.NotionClient", FakeCls)`).
对比 PR-4 试图 mock 整个 AsyncClient 复杂得多。
关键是 CLI 命令 import 路径要稳定 (e.g. `from src.notion.client import NotionClient` at module level, 不在函数内 import).

### 6. 边界 case 补测试是 ship 阶段的工作
PR-5 主体 11 个 story 加了 27 个测试; 离 ≥ 650 门槛差 11。
单独跑一次 codex 补 11 个边界 case (US-012 prep, commit d45e6fd) 把总数推到 650 — 比每个 story 都强求 +5 case 更高效, 因为边界 case 是"看现有覆盖找缝隙", 一次性扫一遍效率高。

### 7. PR-5 没破坏 PR-4 的任何 contract
DB_VERSION 不变 / 10 个 CLI group 不变 / 45+ schema 仅 oneOf 扩 / 退出码体系不变 / pm2 检测 + auth 模式不变 / batch + LongTaskContext 行为不变。
唯一加性 drift: admin cleanup-deadletter 因共享 schema 也得了 mode=inline + ok 字段 (无负面影响)。
