## A. 检索完整性（建议第一批）

反馈：https://app.notion.com/p/3d615375830d812cb011cc6032eca589

### 已证实

- `frontend/src/ai-gateway/tools/schemas.ts:69` 中 `is_read`、`is_flagged` 都为 `z.boolean().optional()`。用本机安装的 AI SDK `zodSchema` 转换这段实际 schema，生成 JSON Schema 没有 required，省略解析成功；null 解析失败。
- `frontend/src/ai-gateway/tools/email.ts` 将两个值原样传给 domain client；`src/api/routers/email.py` 默认 None；`src/repository/email_repository.py:1463` 仅非 None 时增加过滤。false 明确表示仅未读/未旗标，不能表示不限。
- 因此当前工具和后端已有“省略即不限”，只做“改成 optional”不会修到问题。尚未取得用户当次模型请求的最终工具 schema，无法证明服务商/上游是否重新收紧 schema，也不能仅凭助手自述证明它必填。
- 全文 API 只给命中、索引总量等信息，没有相关元数据候选的正文缺口。gateway 投影甚至未保留 total_indexed。`email_body` 对正文缺失报 E_NOT_FOUND，不能充分区分“邮件不存在”与“元数据在、正文缺失”。
- `src/mail/new_watcher.py:1850` 日期过滤在 `_maybe_dual_write_body` 之前，提前 return 可造成有元数据无正文。`mark_skipped` 清空 sync_error，没有结构化跳过原因。
- `src/sync/backfill_builders.py:137` 回填候选限制 `sync_status='synced' AND notion_page_id IS NOT NULL`；该反馈中的 skipped、无 Notion 页面邮件不会被选中，force 也不取消这两道限制。

### 用户个案的证据边界

目标 ID 为 1000035394，反馈给出的邮件日期为 2025-12-20。诊断包配置为 fixed、SYNC_START_DATE=2026-01-01，与日期跳过路径吻合，是有依据的首要假设。

包内没有目标 ID 的入库日志；db_check 显示 ran=false，包内也没有用户数据库。本机开发库没有该 ID，不能代替用户库检查 body/FTS。日志中有 AP9770 搜索请求，但没有完整工具入参和返回计数，无法独立重放“0→5 条”和 USD 185 正文。个案正文缺失目前依据反馈中的工具返回证据，不能升级成已在用户库独立复现。

### 拟实施方案

1. 保留现有布尔参数兼容，增加清晰字段说明：省略/null 不限，false 是反向筛选；nullable 在网关归一为 undefined，不把 null 当 false。无用户要求时不按已读/旗标缩小历史检索。返回 effective_filters，包括默认排除草稿的范围。
2. 对支持的 provider 协议做最终请求 schema 契约测试；仅当实际请求捕获证明某上游强制必填时，修该适配层，不全局改写全部工具 schema。
3. 搜索内核增加独立 coverage 信息：根据可安全提取的 subject/from/date/mailbox 等元数据约束，报告相关候选中正文缺失/不可检索的数量和有限样例。不得把候选放进正文 hits、不得声称它们包含查询价格。复杂 OR/否定无法准确投影时标注覆盖未知；无收窄条件只给全局覆盖概况。索引状态须核对实际检索通道，不能仅用 sync_status 推断。
4. API、gateway、搜索 UI 共用覆盖契约；单封读取区分 metadata_missing、body_missing、format_missing，提供可操作的补取入口。正文缺失时，Agent 在结论中说明资料不完整，并检查后续线程，不能把旧引用当最终批准价。
5. 将已经抓取成功的 MIME 正文保存与 Notion 日期过滤解耦：本地正文保存后再决定是否写 Notion。不会仅因此调整自动遍历所有历史邮件。
6. 增加按 ID 的本地正文补取路径，复用 backend 抓取、解析和 repository 入库；支持 skipped/无 Notion 页，不借道强制 Notion resync。保留具体跳过原因；历史未知原因保持 unknown，不批量伪造日期归因。
7. 经用户确认后在受影响环境先补取目标单封，再验证 `subject:AP9770 185` 和线程证据。批量回填另做缺口统计、分批限速与检查点；不把小修变成全库重同步。

验收：已读/未读×旗标/非旗标四组合在默认查询均可返回；省略与 null 等价，true/false 仍准确；覆盖提示和命中严格分离；正文补取后正文与对应索引可查；Notion 日期边界仍成立；模型不得在资料不完整时宣称最新价格已核实。

## B. 今日页待回处理与刷新（建议第二批）

反馈：
- https://app.notion.com/p/3d515375830d81c7b1b8f8cedb3f8e5e
- https://app.notion.com/p/3d515375830d81f299d6d2d1de6ac02e

### 证据

`src/today/aggregate.py` 的口径为收件箱、需要回复/需要决策、近 7 天、线程内没有更晚的我方发件，等得最久优先，最多 30 条。截图有等 5 天、4 天和 21 小时的邮件，不能据此认定未更新；同线程多封候选也可能分别出现。发件箱同步不完整或线程缺失会造成已回复仍显示，当前没有此用户日志证明这种情况。

`TodaySectionRow.tsx` 对邮件仅提供打开/去回复。事项关注信号虽然已有 dismiss，并不适用于这些邮件行。

`useTodayData.ts` 的 nowMs 来自 runs.dataUpdatedAt 或首次打开时间，未有独立时钟。`useTodaySections.ts` 的当天窗口跟着它走；staleTime 只表示过期，不是定时刷新。today 聚合虽有聚焦刷新与三类邮件/分类事件失效，其他源刷新并不必然推进 runs 时间。页面常驻无对应事件时，跨日窗口、相对时间、7 天退场存在滞后风险。此为代码可确认的风险，尚未做跨日 UI 复现，也未证明它就是截图成因。

### 拟实施方案

1. 给页面增加统一、独立的时钟基准；分钟级更新时间文字，跨本地日界、恢复可见/唤醒时更新日期窗口及时间敏感请求。后台不高频轮询，前台给今日聚合一个低频兜底；失败显示刷新异常，不能静默当成空列表。
2. 写明“近 7 天待处理，较早邮件优先”，保留跨日未处理事项；不以仅显示当天邮件掩盖欠账。
3. 增加“无需回复”和撤销。采用后端持久化的单封待回处理状态，保留 AI 原始分类；重分类/刷新不得覆盖人工决定。按邮件标识作用，同线程未来新邮件仍可正常提醒。默认只处理该封，避免误关整个线程的新请求。
4. mutation 后实时失效 today query，失败回滚乐观移除。检查发件入库/归档等实际写路径是否触发相关刷新，再补缺口。手工状态与通知已读、事项信号处理状态保持各自语义。

验收：无需回复立即退出、重启不回弹、可撤销；同线程新邮件仍出现；已回判据回归；跨午夜、睡眠唤醒、断线恢复及聚焦刷新；超 7 天准确退出；今天日历窗口随日期推进。

风险：新增持久状态需要幂等迁移及 DB_VERSION/前端 EXPECTED_DB_VERSION 对齐。截图用户未提供诊断包，所以不能声称同步故障已定位或统计受影响人数。

## 补充设计：线程待回与邮件多标签（用户追加讨论，尚未批准实施）

本节补充并细化 B/C；涉及线程批量关闭时，以本节的明确作用范围为准。

> 后续批准记录：用户于本会话 2026-09-09 授权实施，并最终修正为 **Pin（主动保留）与编辑保护独立**。编辑时允许取消 Pin，未保存圆点仍保护现场；发送结束且编辑保护解除后，无 Pin 的标签可以被后续浏览替换。移除“浏览中”文字，hover/focus 提供 Pin 操作。本节以下早期“编辑自动转保留”的草案文字以此修正及 `.trellis/tasks/09-09-feedback-tabs/prd.md` 为准。

### 待回邮件按线程聚合

- 一行一个 thread_id，默认折叠；不根据主题文本自动合并。无有效线程 ID 的邮件按单封独立显示。
- 先按现有待回规则筛候选，再按线程分组，最后对线程数排序/限额；不能先截 30 封再分组，否则同一线程仍会挤掉其他线程。
- 行标题取最新待回候选的主题，显示最近发件人、最近来信时间、待处理封数；最早未处理候选的等待时间用于排序和“最早已等 N 天”。最近来信与最早等待明确分开。
- 主区和导航徽标统一显示“X 个待回会话”，可辅以“共 Y 封待处理邮件”。Y 指待回候选数，不冒充完整线程总邮件数。
- 左侧箭头展开当前线程的待回候选，默认新到旧；标题打开最新待回邮件的线程上下文。展开不另开标签。用户可打开指定子邮件，或查看完整往来。
- 保留现有已回判据；有线程新消息不代表旧请求自动解决。折叠状态使用稳定线程键，后台刷新不全部重置。
- 线程行“无需回复”明确表示“当前这 X 封无需回复”，服务端处理本次可见候选 ID 快照，并提供一次撤销；之后收到的新邮件照常判断，不能永久屏蔽整个线程。子邮件也可单独处理。提交时新到的邮件不进入旧快照。
- 验收覆盖同线程多封、相同标题不同线程、无 thread_id、分页/限额在聚合之后、最后一次我方回复之后又有新来信、线程批量关闭与撤销、操作期间新邮件到达。

### 推荐的标签模型

默认“复用浏览标签”+主动保留+编辑自动保护；另保留一个“点击邮件时：复用浏览标签（默认）/每封新开标签”的偏好。保护编辑与已保留标签的规则不受偏好控制。

概念上只区分一个可替换的浏览标签和多个保留标签。浏览标签标注轻量“浏览中”，菜单提供“保留标签”；保留后标记消失。编辑状态另用编辑图标，不用同一图标同时表示保留和未保存。

| 动作 | 默认行为 |
| --- | --- |
| 单击列表、线程待回项或搜索结果 | 优先激活已有目标；否则复用唯一浏览标签，没有则创建 |
| 双击邮件行 | 保留该邮件；如果第一次 click 已预览它，则就地提升为保留标签，不复制 |
| 右键“在新标签页打开” | 打开/激活并保留该目标；菜单是可发现的正式入口 |
| 浏览标签上选择“保留标签” | 当前标签转保留，不额外创建 |
| 在浏览邮件中打开回复/转发 composer | 立即转保留，即使还未输入内容 |
| 编辑 A 时点击 B | 保留 A，打开/复用独立浏览标签 B；继续点 C 则 B→C，A 仍在 |
| 在 B 中也开始写回复 | B 也转保留，后续普通浏览使用新的唯一浏览标签 |
| 回复发送成功或取消编辑 | 标签仍保留；不能突然降级成下一次点击即可替换 |
| 开启“每封新开” | 单击不同目标创建保留标签；同目标仍去重 |
| 切换偏好 | 仅改变后续点击，已有标签原样保留 |

双击语义是“保留这封”，不是“复制这封”。第一次单击可以立即显示内容，无需为了等待双击延迟所有浏览。此前的临时浏览内容允许被替换；需要保留原浏览内容时先保留它，或使用右键新开。已保留的标签始终不受这条替换规则影响。

### 边界与状态保护

- 不把“替换当前任意标签”当实现：用户从事项、对话、报告切入邮件，仍只寻找邮件浏览槽，不能替换其他对象。
- 已绑定邮件对话的标签也提升为保留，沿用当前不原位替换会话标签的约束。
- 默认模式下，点击已有保留标签只激活它，不把它重新标为浏览；随后普通点击仍复用原来的浏览槽。
- composer 快照必须覆盖正文、收件人/抄送、附件、光标/选区、滚动位置及当前模式；IME 输入未结束时也不能丢字。切换前保存内存状态，切回后恢复。自动保存草稿不能替代这些交互状态。
- 主动保留/编辑标签不再因邮件普通浏览被 LRU 静默关闭。保留现有容量约束时，满额通过明确提示和管理入口处理；不得为了打开新邮件清掉保留工作。实现前核对共享上限对其他对象标签的影响。
- 首次升级将现存标签视为保留，避免下次点击意外替换旧工作。标签类型与偏好随重启持久化；编辑恢复沿用已有草稿链，不能承诺仅凭内存快照跨崩溃恢复。
- J/K 在浏览标签中原位切换；在保留/编辑标签中则走浏览槽，不覆盖该工作。右键新开、双击提升、键盘“保留标签”必须统一到同一动作。
- 不直接占用 Cmd/Ctrl+单击：先审计邮件列表现有多选手势，避免与多选冲突。首批以单击、双击和右键菜单完成闭环。

选择理由：仅用“单击复用当前标签”不能保护主动保留但未编辑的工作；仅增加配置会让希望多数时候浏览、偶尔并行的用户反复切换设置。一个默认浏览槽让普通用户无需整理标签，主动保留与编辑自动提升提供多任务能力，配置仅兼容始终新开的个人偏好。

场景验收：浏览 20 封保持一个浏览标签；A 编辑→B/C 浏览只增加一个浏览标签；A/B 同时编辑均完整保留；双击不产生重复；主动保留 C 后普通浏览不覆盖 C；关满额提示不造成数据丢失；重启偏好/保留语义不变；中英文、键盘、触控和窄窗口可用。
