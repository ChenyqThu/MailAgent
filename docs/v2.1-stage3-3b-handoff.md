## 1. 3b 目标 + 范围

**目标**：让 chat 引擎（已在 shared）能在「无 better-sqlite3、无 LLM key、无 execa」的 UI 进程跑 —— 即定义并实现 `HttpChatPlatform`（fetch serve-api），serve-api 补齐 chat 后端端点。**3b 不接 renderer transport、不删 main 直跑**（那是 3c）。3b 完成 = 本地 electron 路径零回归 + serve-api 端点齐备 + HttpChatPlatform 单测过。

**范围**（设计 §6 + 矩阵 3b 行）：
1. **模型板/工具板定形**：按 custom_api/notion_agent/工具/KOS 的真实需要定 `ChatModelPlatform`（`llmFetch` / `notionAgentStream` / `getCachedSenderDigest`）+ `ChatToolPlatform`（工具集 / `saveToKos`）于 `platform.ts`。
2. **custom-api SSE 解析下沉 shared**：`CustomApiBackend` 的解析逻辑 → `shared/chat/backends/custom_api.ts`，HTTP fetch（注入 key）经 `platform.llmFetch(req) → Response`（body = 原始 Anthropic/OpenAI SSE）。ElectronModelPlatform.llmFetch = 本地 fetch + 注入 key；serve-api `POST /api/chat/llm-proxy`（注入 key + StreamingResponse 透传）。
3. **notion-agent 复刻 Python**：serve-api `POST /api/chat/notion-agent`（asyncio spawn 子进程复刻 NotionAgentBackend 语义）；`platform.notionAgentStream(req) → AsyncIterable<ChatStreamEvent>`。electron impl = 现有 execa（留 main，notion_agent.ts 不下沉）。
4. **chat 持久化写端点**：serve-api `POST/PATCH /api/chat/*`（镜像 chat_db 写：appendMessage/streamContent/finalizeMessage/appendToolCall/updateToolCall/abortStreamingMessages/getOrCreateSession/...）；HttpChatPlatform.persist 实现 = fetch 这些端点，**`streamContent` 在此做 debounce（~1/s 合并 PATCH）+ `finalizeMessage` 先 flush 再写终态**（D1，见 platform.ts ChatPersistPort 注释）。
5. **工具端点 + KOS 代理**：写工具（flag/archive/draft/kos_put）经 serve-api（D1 已有 `/api/email/*` 部分）+ KOS（kos_query/kos_digest/saveToKos）经 serve-api 代理。
6. **HttpChatPlatform 组装**：实现全部板（Infra+Model+Tool）= fetch 上述端点 + 单测（mock fetch）。

## 2. 关键设计输入 / 决策（动手前吃透）

- **D1 持久化 cadence 由 platform 控**：harness 每 chunk 调 `platform.persist.streamContent`（fire-and-forget void）。electron = 同步 `updateMessage`（零回归）；http = debounce ~1/s 合并 PATCH，`finalizeMessage` **先 flush 该 msg 待发增量再写终态**（防终态被旧增量覆盖；harness 所有终态 patch 已带 `content=buffer` 做双保险，steps3-4 review MEDIUM-2）。
- **D2 custom-api 解析留 shared / notion-agent 复刻 Python**：按后端性质分（HTTP 可代理/浏览器解析 vs 子进程必服务端）。两者各自单实现 → 零 parity。
- **D3 3b 不搬执行进 renderer**（那是 3c）。3b 只做后端端点 + HttpChatPlatform impl，electron 路径继续零回归。
- **D4 notion-agent 也走 harness**（empty tools 首轮 `collected.length===0` 即 end_turn = 等价单遍）。**注意**：3a 为零回归**保留了 dispatcher legacy 单遍**（notion-agent 当前走 legacy）；D4「删 legacy 单遍」推迟到 3c（设计 §4 D4 + handoff 历史标注 D4 删 legacy 3c）。3b 不强制删 legacy。
- **D5 本地也走 serve-api**：3c cutover 后本地 renderer 也经 serve-api。3b 的 ElectronChatPlatform 仍是过渡（直调保零回归）。

**🟡 待澄清/决策（3b 详设第一步定）**：
- **HttpChatPlatform 归属**：设计 §6 说 `shared/web`，但**当前无 `frontend/src/shared/web/` 目录**（shared/ 下有 api/chat/components/... 无 web）。候选：① 新建 `shared/web/`（与设计一致）② 放 `shared/chat/http_platform.ts`（就近 platform.ts）。**注意不变式 1**：HttpChatPlatform 用 `fetch`（浏览器/Node 全局，非 Electron），可进 shared；但若它 import `HttpApi`（shared/api）要确认 HttpApi 本身零 Electron。建议详设时拍板 + `pnpm build:web` 验。
- **矩阵 httpPlatform 行标 3c**（line 67）vs 设计 §6 归 3b：以**设计 §6 为准（HttpChatPlatform impl 归 3b）**，3c 只做 transport 接线（renderer 注入 HttpChatPlatform 跑 harness）+ confirmation UI + 删 main 直跑。详设时同步修矩阵这格的阶段标注。
- **ChatModelPlatform 是否并入 ElectronChatPlatform 单对象**：3a 的 ElectronChatPlatform 是单对象实现 Infra 板。3b 模型/工具板可扩到同对象（TS 结构化兼容，harness/backend 形参各取所需板），或拆 ElectronModelPlatform。设计 §3.4「单一实现类」倾向同对象。详设拍板。
