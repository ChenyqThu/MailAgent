## 2. B-pure-unified 目标架构

harness/dispatcher/dispatch/backends 逻辑**搬到 `shared/chat/`，跑在 UI 进程**（本地 renderer / 远程 browser），经一份 `ChatPlatform` → 一份 serve-api：

```
┌ UI 进程（shared React + shared/chat harness 跑在这里）──────────────┐
│  harness loop → ChatPlatform 原语                                    │
│    · 流式 token 直接 emit 给 React（无 IPC，无跨进程推流）           │
│    · confirmation = React 弹窗 → 直接 resolve promise（同进程，无 IPC）│
└──────────────────────────┬──────────────────────────────────────────┘
              本地 renderer │ 远程 browser
         token: main webRequest 注入 │ CF cookie
                           ▼
            ┌ serve-api (FastAPI 8200，唯一 chat 后端) ┐
            │ POST /api/chat/llm-proxy   (注入 key, 透传 Anthropic/OpenAI SSE 不解析) │
            │ POST /api/chat/notion-agent(asyncio spawn CLI, 复刻 thread/gate/exit)   │
            │ chat 持久化端点 (镜像 chat_db 写)                                       │
            │ 工具端点 /api/email/* (D1 已有读写) · KOS 代理                          │
            └────────────────────────────────────────────────────────────────────────┘
```

**两类后端的不对称（有意，按性质分）**：
- **custom-api = HTTP**：serve-api `llm-proxy` 注入 key 后**透传原始 SSE**，shared custom_api 在 UI 进程**解析**（解析逻辑单一真源在 shared）。`platform.llmFetch(req) → Response`。
- **notion-agent = 子进程**：execa 不能在浏览器跑，spawn+解析 stdout+thread 探测（需 fs）天然在服务端。serve-api Python **复刻** `notion_agent.ts` 的 spawn/解析/gate/exit 分类，`platform.notionAgentStream` 直接 yield 语义 event。TS `notion_agent.ts` 删除。
- 两者最终都是**单一实现**（custom_api=shared TS / notion_agent=Python）→ 零 parity 守住。notion-agent 的 Python 复刻是 3b 的硬骨头（thread 探测/gate/exit code 75/77/127 分类必须逐一对齐，有单测 `notion_agent_gate.test.ts` 钉）。

## 3. ChatPlatform 接口（分层接线板，本设计核心）

> **架构基准（用户拍板「分层接线板」2026-06-05）**：不把外部能力堆成一个大
> interface，而按「变更频率 + 职责」拆成几块独立小板，组件各取所需的板。红利：
> 未来海量工具/后端补充只动对应板 interface + 各端实现，**地基板与 harness/
> dispatcher 核心零改动**。原「9 原语单接口」草案已废（见 §3.5 演进记录）。

`frontend/src/shared/chat/platform.ts`（**零 Electron/Node 依赖**，只引 `shared/chat` 内类型）。

### 3.1 板划分

| 板 | 定形 | 含 | 消费方 |
|---|:---:|---|---|
| **基础设施板** `ChatInfraPlatform` | **3a** | persist（ai_chat.db 写读）/ loadEmailContext / resolveConfig / prefetchSenderDigest | harness + dispatcher |
| **模型板** `ChatModelPlatform` | 3b | llmFetch（custom-api SSE）/ notionAgentStream / getCachedSenderDigest | custom_api/notion_agent 下沉时 |
| **工具板** `ChatToolPlatform` | 3b | 工具集（email_*/flag/draft/attachment/kos_query…）/ saveToKos | tools/builtin + kos_save 下沉时 |

**为何 3a 只定基础设施板**：grep 实测 harness + dispatcher 的全部外部调用只落这 4 类
（见 §1 依赖面）。模型板/工具板的 7 原语，其消费方（两后端 / 工具 / KOS 保存）3a 全留
main 走现有注入口（`args.backend` / `args.registry` / `chat:saveToKos` channel），根本不调
platform → 3a 写它们 = 无消费方的占位假线。按真实形状 3b 定形，避免「猜的形状 3b 还得改」。

### 3.2 基础设施板接口（3a 定形）

```typescript
// 持久化端口（ai_chat.db 写读）。全部方法 Promise（http 异步）；streamContent
// 例外 = fire-and-forget void（守 harness 每 chunk 同步写零回归）。
export interface ChatPersistPort {
  getOrCreateSession(input: OpenSessionInput): Promise<ChatSession>
  createNewSession(input: OpenSessionInput): Promise<ChatSession>
  getSession(sessionId: number): Promise<ChatSession | null>
  getMessage(messageId: number): Promise<ChatMessage | null>
  listLastNMessages(sessionId: number, limit: number): Promise<ChatMessage[]>
  appendMessage(input: AppendMessageInput): Promise<ChatMessage>
  /** 流式正文增量。fire-and-forget，不 await（守 harness 每 chunk 同步写热路径
   *  零回归）。electron 同步直写；http debounce ~1/s 合并 PATCH。 */
  streamContent(messageId: number, content: string): void
  /** 终态（complete/error/aborted + token/cost/model/metadata）。await；http
   *  先 flush 取消该 msg 待发 streamContent 增量，防终态被旧增量覆盖。 */
  finalizeMessage(messageId: number, patch: UpdateMessagePatch): Promise<void>
  deleteMessagesFromId(sessionId: number, fromMessageId: number): Promise<number>
  abortStreamingMessages(sessionId: number): Promise<number>
  appendToolCall(input: AppendToolCallInput): Promise<{ id: number }>
  updateToolCall(toolCallId: number, patch: UpdateToolCallPatch): Promise<void>
  getToolCallByUseId(messageId: number, toolUseId: string): Promise<{ id: number } | null>
}

// 运行配置快照（env 读，harness 启动时一次性取）
export interface ChatRuntimeConfig {
  maxIter: number               // AGENT_MAX_ITER (默认 8)
  maxCostUsd: number            // AGENT_MAX_COST_USD (默认 0.5)
  kosL1HotBlockEnabled: boolean // MAILAGENT_KOS_L1_HOT_BLOCK_ENABLED
  harnessEnabled: boolean       // MAILAGENT_AGENT_HARNESS (默认 ON)
}

export interface ChatInfraPlatform {
  persist: ChatPersistPort
  loadEmailContext(emailId: number): Promise<EmailContext | null>
  resolveConfig(): Promise<ChatRuntimeConfig>
  prefetchSenderDigest(senderAddr: string): void
}
```

**`backendSupportsTools(kind)` 不进 platform**：纯 `BackendKind→bool` 静态能力映射，
下沉 `shared/chat/model.ts`（dispatcher harness-vs-legacy gate 用）。它是 model 层知识、
非 env 配置，故不进 `resolveConfig`；未来加 backend 在此一处扩。

### 3.3 模型板 / 工具板（3b 定形，3a 仅占位注释）

3a 的 `platform.ts` 只写注释说明这两块板的归属，**不写空 interface**（避免无消费方假线）。
3b custom_api/notion_agent 下沉时定义 `ChatModelPlatform`（`llmFetch` 返回原始 SSE
`Response` / `notionAgentStream` yield 语义 event / `getCachedSenderDigest` 与 prefetch
配对）；tools/builtin + kos_save 下沉时定义 `ChatToolPlatform`。

### 3.4 实现与消费

- **单一实现类**：main 侧 `ElectronChatPlatform`（`src/electron/main/chat/electron_platform.ts`，
  **非 shared**）实现**所有板**（3a 只需实现基础设施板成员，直调既有 chat_db/db/config/kos，
  `streamContent`=同步 `updateMessage` 零回归）；3c 远程 `HttpChatPlatform`（shared/web）同理。
- **按需消费**：harness/dispatcher 形参类型 = `ChatInfraPlatform`（只声明依赖基础设施板），
  传入 `ElectronChatPlatform` 实例（TS 结构化兼容）。3b backend factory 形参 = `ChatModelPlatform`。
- **类型归属**：`ChatMessage/ChatSession/BackendKind/ConfirmationTier/EmailContext/ChatStreamEvent`
  已下沉 `shared/chat/model.ts`+`types.ts`（steps 1-2b ✅），`chat_db.ts`（better-sqlite3 留 main）
  **re-export** 保既有 importer 路径不变。

**sink + confirmation 不进 platform**（已是注入式抽象，跨平台 impl 不同接口不变）：
- `HarnessSink.send(envelope)`：production impl 从 `webContents.send` 换**进程内 emitter**（React 订阅）。
- `awaitConfirmation/resolveConfirmation`：保留 module map；React 弹窗**同进程**直调 resolve（不经 IPC）。

### 3.5 演进记录

- **单接口草案**（一个 `ChatPlatform` 含 persist/loadEmailContext/llmFetch/notionAgentStream/

## 4. 关键设计决策（已定，非开放 fork —— 多数是已选架构的推论）

| # | 决策 | 理由 / 备选 |
|---|---|---|
| D1 | **持久化 cadence 由 platform 控**：harness 每 chunk 调 `streamContent`（逻辑不变），electron 同步直写、http debounce ~1/s+finalize flush。把 updateMessage 拆成 `streamContent`(debounced) + `finalizeMessage`(awaited 终态)。 | 守「harness 逻辑单一真源」。备选「harness 改成只在 checkpoint 持久化」会把 IO 策略漏进逻辑层，pass。 |
| D2 | **custom-api 解析留 shared，notion-agent 复刻 Python**：按后端性质分（HTTP 可代理可浏览器解析 / 子进程必服务端）。两者各自单实现 → 零 parity。 | execa 无法浏览器跑是硬约束；强行统一只会更糙。 |
| D3 | **3a 保持 harness 仍跑在 main**（经 `ElectronChatPlatform` 包既有 chat_db/handlers/backends，**字节级零回归**）；**3c 才把执行搬进 renderer**（`HttpChatPlatform`）+ 删 main 直跑路径。 | 每 phase 可独立验证：3a=纯重构（既有单测全绿）、3c=cutover。一次性搬执行+换传输风险叠加。 |
| D4 | **notion-agent 不再走 legacy 单遍**，统一进 shared harness（empty tools → 首轮 `collected.length===0` 即 end_turn = 等价单遍）。删 dispatcher 内联 legacy 路径。 | 消除双路径（不变式 3）。等价性由既有 dispatcher/harness 单测钉。 |
| D5 | **本地也走 serve-api**（用户拍板，零 parity）。3a 的 `ElectronChatPlatform` 是过渡（直调 chat_db 保零回归）；3c 后本地 renderer 同样经 serve-api。`llmFetch` 本地走 loopback serve-api llm-proxy。 | 本地 renderer 也无 better-sqlite3，执行搬 renderer 后必经 serve-api。 |

## 5. 3a 抽取步骤（可验证，每步 `pnpm build:web` 验无 Electron 泄漏 + `pnpm test` 绿）

## 6. 3b 详设（2026-06-05 拍板）+ 3c 概要

> 3a 落地后对 chat 模块 5 类外部能力的真实形状做了完整测绘（serve-api 14 端点 / 20 工具 /
> 两 backend / HttpApi / 鉴权 / KOS），据此定形模型板/工具板 + serve-api 端点契约 +

### 6.0 3b-0 详设拍板（4 个 fork）

| # | fork | 拍板 | 理由 |

#### 6.6.2 ChatRuntime（`shared/chat/runtime.ts`，零 Electron）

封装 `createChatDispatcher` + `HttpChatPlatform` + 进程内 emitter sink，实现**完整 `ChatApi`**（读+跑单一真源）；electron/web 唯一差异 = baseUrl + reads + 鉴权（全对 runtime 透明）。

```typescript
export interface ChatRuntimeDeps {
  /** HttpChatPlatform 工具读委托（reads.email/attachment）。web=HttpApi 自身；
   *  electron=new HttpApi(loopback)。**不**用 reads.chat（避免与本 runtime 循环）。 */
  reads: MailApi
  /** persist/llm-proxy/notion-agent/kos/chat 读 fetch 基址（同 HttpApi baseUrl）。 */
  baseUrl: string
}
export function createChatRuntime(deps: ChatRuntimeDeps): ChatApi
```

- **emitter + sink 构造期即建**（`onStream` 在首次 `start` 前就被 `useEmailChat` effect#2 订阅）：`emitter=new ChatStreamEmitter()`；`sink={send:(env)=>emitter.emit(env)}`。
- **dispatcher/platform/registry/backends lazy**（需 await `/chat/config`）：首次跑方法前 `ensureEngine()` —— `snap=await request(baseUrl,'GET','/chat/config')` → `platform=new HttpChatPlatform(reads,baseUrl,toHttpConfig(snap))` → `registry=createToolRegistry(); createBuiltinTools(platform)` 注册（`kosConfigured` gate 9 KOS 工具）→ `backends={'custom-api':createCustomApiBackend(platform),'notion-agent':createHttpNotionAgentBackend(platform)}` → `dispatcher=createChatDispatcher({platform,getBackend:k=>backends[k],toolRegistry:registry})`；缓存 `{dispatcher,platform}`。
- **方法映射**（mirror `ChatApi`）：`start`/`editMessage`→`(await ensureEngine()).dispatcher.startChat/editChatMessage(map(opts),sink)`；`abort(sid)`→`void ensureEngine().then(e=>e.dispatcher.abortChatSession(sid)).catch(warn)`（fire-and-forget）；`confirmTool(id,ok,edited)`→**同进程** `resolveConfirmation(id,{approved:ok,editedInput:ok?edited:undefined})` 包 `{ok}`/`{ok:false,E_NOT_PENDING}`（无 ensureEngine——map 已被跑中 harness 注册）；`newSession`→`platform.persist.createNewSession`；`saveToKos`→`platform.saveToKos` 包 envelope；`onStream(h)`→`emitter.subscribe(h)`（同步）；读 `listMessages/listSessions/listAllSessions/listToolCalls/kosAvailable`→fetch `baseUrl/chat/*`（迁阶段 2 HttpApi chat 读逻辑，单一真源，catch 返 []/null）。
- **接线**：web=`HttpApi` 构造 `this.chat=createChatRuntime({reads:this,baseUrl})`；electron=`ElectronApi` 构造 `this.chat=createChatRuntime({reads:new HttpApi(LOOPBACK),baseUrl:LOOPBACK})`。

session.defaultSession.webRequest.onBeforeSendHeaders(filter, (d, cb) =>

serve-api 读 `config.py`/env（无副作用，鉴权同其他 chat 端点）；`HttpApi` 加 chat config 读方法供 runtime 预取。**注意** electron `chat/config.ts` getter 与 serve-api `config.py` env 同源（同机 .env/注入），但 `kosConfigured` 语义须刻意对齐（3b-4 electron=`isKosConsumerEnabled()` 注册 gate 语义，非 OAuth 凭据齐）。

#### 6.6.5 cutover（删 main 直跑 + D4 + migrate 保留，3c-4）

## 8. 风险 / 不变式

- 🔴 **不变式 1**：`shared/chat/` 零 Electron/Node-only 依赖。3a 每子步 `pnpm build:web` 验证。方案成败根本。
- 🔴 **本地 chat 回归**：3a 经 ElectronChatPlatform 保零回归（既有单测钉）；3c cutover 后本地依赖 serve-api 在跑（C2 软门控+崩溃自拉起兜底，失离线独立）。
- 🟡 **notion-agent Python 复刻 parity**：thread 探测 / gate / exit 75/77/127 分类逐一对齐，`notion_agent_gate.test.ts` + 新 Python 测钉。
- 🟡 **debounce 正确性**：streamContent/finalizeMessage 拆分 + http impl 取消待发增量，防终态被旧增量覆盖。3b/3c 专测。
- 🟡 **本地流式 transport**（3c）：webRequest 注入 token + serve-api CORS（推荐，httpPlatform 一份）vs IPC+MessagePort（备选）。3c 先验推荐路径。
- 工期：3a ~1w（重构+测）+ 3b ~1-1.5w（serve-api 端点+Python 复刻）+ 3c ~0.5-1w（transport+cutover+e2e）≈ 2.5-3w。
