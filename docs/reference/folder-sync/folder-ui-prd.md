# 存档邮件 + 草稿箱 — UI 设计需求 (PRD)

> 给设计师（claude design）的输入文档。描述**功能需求 / 数据能力 / 交互流程 / 设计系统约束**，
> 布局与视觉细节由设计师发挥。产出 mockup 后，工程按 mockup 实现（**只重做 UI 层组件，
> 后端数据管道 + IPC + 类型已就绪不变**）。

## 0. 一句话

为 MailAgent 桌面客户端新增「存档」「草稿箱」两个邮箱入口，需要**与现有收件箱风格高度一致**
的 list + 详情 + 操作 UI。当前已有一版工程实现，但视觉/体验不满意，需要重新设计。

---

## 1. 背景与上下文

- **产品**：MailAgent — macOS 邮件客户端（Electron + React 19 + TanStack Router/Query + Tailwind），
  把公司 Outlook/Exchange 邮件（经 DavMail IMAP 桥）同步到本地 SQLite，本地秒级读取。
- **现有视图**：左侧 Sidebar（账户头 + MAILBOXES 段：收件箱/发件箱/已标旗/所有邮件 + AI AGENTS 段 + VIEW 段）；
  主区是经典**两栏**：邮件列表列 + 邮件详情列。
- **本次新增**：Sidebar MAILBOXES 段加「存档」「草稿箱」两个入口，各自一套 list + 详情。
- **用户**：单用户（开发者本人 dogfood），高频处理邮件，重信息密度 + 操作效率 + 视觉精致度。

## 2. 设计系统约束（必须严格遵循，保证与收件箱一致）

设计**不能**引入新的设计语言。必须复用现有 token 与组件语汇：

**颜色（CSS 变量 / Tailwind token）**
- 背景层次：`ink-0`→`ink-5`（由深到浅），`glass`/`glass-2`/`glass-3`（毛玻璃面板，列表列用 glass-2、详情列用 glass-3）
- 前景文字：`ink-fg`（主）/`ink-fg-1`/`ink-fg-2`/`ink-fg-3`（渐弱）
- 描边：`ink-border` / `ink-border-soft`
- 强调色：`coral` / `coral-hover` / `coral-dim`（主 CTA、选中态、链接）
- 语义色：`ok`(绿) / `warn`(黄) / `fail`(红) / `info`(蓝) / `ai`(紫)
- 优先级色（收件箱 AI 用，存档/草稿**不用**）：`crit`/`urg`/`impt`/`norm`/`low`

**字号（行高）**：`text-micro` 11/14 · `text-meta` 12/16 · `text-aux` 14/20 · `text-body` 14/20 · `text-lead` 15/22 · `text-subj` 22/30

**组件库**：Radix UI（dialog / select / tabs / tooltip / switch 等）+ lucide-react 图标（线性，size 13-16，strokeWidth 1.75-2）

**现有可复用的视觉语汇**（设计应延续其风格）：
- 收件箱列表行 `.email-row`：头像/monogram + 发件人 + 时间 + 主题 + 正文摘要 snippet + 右侧操作图标 + 未读加粗 + 选中 wash
- 详情头：大主题（text-subj）+ From/To/Date/… 元数据网格（label 列等宽 + 值列）
- 48px 顶部 toolbar：`GhostBtn` 幽灵按钮（icon + 可选 label，自适应密度：宽→显 label，窄→仅 icon + hover tooltip）
- 正文：DOMPurify 净化后的 sandboxed iframe 渲染 HTML

> 设计师可参考现有 `frontend/ref/mockup-inbox.html`（收件箱设计稿）作为风格基准。

## 3. 功能范围

### 3.1 存档 (Archive) — 已归档的历史邮件，只读为主 + 少量运维操作

| 能力 | 说明 |
|---|---|
| **列表** | 显示存档文件夹邮件，按时间倒序。每行：发件人、主题、时间、正文摘要、附件标记、旗标标记 |
| **详情** | 主题 + From/To/Cc/Date 元数据 + 正文（HTML 渲染）+ 附件列表（只读，展示文件名/大小/类型）|
| **移回收件箱** | 把存档邮件移回 INBOX（移回后会重新出现在收件箱）。**需二次确认** |
| **永久删除** | 从邮件服务器永久删除。**危险操作，需二次确认（强调不可逆）** |
| **搜索**（可选 P1）| 对存档全文搜索（后端 FTS5 已就绪，支持中文）|

### 3.2 草稿箱 (Drafts) — 自己撰写中的邮件，可编辑/发送/删除

| 能力 | 说明 |
|---|---|
| **列表** | 显示草稿，按最后修改时间倒序。每行：收件人（草稿的重点是「发给谁」，非发件人）、主题、时间、正文摘要、附件标记 |
| **详情** | 主题 + From（自己）/To/Cc/Date + 正文 + 附件 |
| **新建草稿** | 从空白创建：填收件人/抄送/主题 + 富文本正文 |
| **编辑草稿** | 修改已有草稿内容（收件人/主题/正文）|
| **发送** | 把草稿真实发出（SMTP）。**对外不可逆，需二次确认** |
| **删除** | 删除草稿。**需二次确认** |

### 3.3 撰写器（新建 + 编辑共用）

- 收件人 / 抄送 / 主题 输入区（收件人支持多个，逗号分隔）
- **富文本正文编辑器**（已用 TipTap）：加粗 / 斜体 / 下划线 / 删除线 / 有序列表 / 无序列表 / 链接 / 行内代码。
  格式工具栏需与设计系统一致（lucide 图标 + ink token）
- 保存 / 取消；发送可在撰写器内或详情 toolbar（设计决定）

## 4. 数据能力边界（设计只能用这些字段，确保可实现）

**列表项 / 详情可用字段**（后端 `folder_email` 表已提供）：

| 字段 | 类型 | 列表 | 详情 | 备注 |
|---|---|---|---|---|
| subject | string | ✓ | ✓ | 主题，可能为空（草稿）|
| sender / sender_name | string | ✓ | ✓ | 存档=发件人；草稿=自己 |
| to_addr / cc_addr | string | 草稿列表用 to | ✓ | 逗号分隔的地址串 |
| date_received | ISO8601 | ✓ | ✓ | 存档=收到时间；草稿=最后修改时间 |
| snippet | string | ✓ | — | 正文前 ~200 字摘要 |
| is_flagged | bool | ✓ | — | 旗标 |
| has_attachments | bool | ✓ | — | 有无附件（角标）|
| attachments[] | {filename, size, content_type} | — | ✓ | 附件**元数据**（名/大小/类型）|
| body_html / body_markdown | string | — | ✓ | 正文 |
| id | number | (key) | (key) | 本地主键 |

**明确没有的字段**（不要设计依赖它们）：
- ❌ **AI 字段**（优先级/分类/动作/摘要）—— 存档/草稿不走 LLM，**没有收件箱那条 AI 信息条**。这是与收件箱列表行的关键区别，设计应更干净。
- ❌ **线程/会话关系** —— 不做线程折叠（草稿/存档按单封展示）
- ❌ **已读/未读**（草稿无此概念；存档不强调）
- ❌ **翻译**（不做沉浸式翻译）

## 5. 交互流程

- **列表 → 详情**：点列表行 → 右侧详情列加载该邮件（同收件箱）
- **存档·移回**：详情 toolbar 点「移回收件箱」→ 确认弹窗 → 成功 toast + 该行从存档列表消失
- **存档·删除** / **草稿·删除**：→ 危险确认弹窗（强调不可逆）→ 成功 toast + 列表移除
- **草稿·新建**：列表区「+ 新建草稿」入口 → 打开空白撰写器（占详情列或覆盖层，设计决定）→ 填写 → 保存 → 回列表，新草稿出现
- **草稿·编辑**：详情 toolbar 点「编辑」→ 撰写器载入该草稿 → 改 → 保存
- **草稿·发送**：→ 二次确认（措辞强调「将真实发出」）→ 成功后草稿从列表消失 + toast
- **自动刷新**：后端有新同步（如在 Outlook 端改了草稿）会通过 SSE 推送，列表**自动刷新**，无需手动

## 6. 状态设计（每个都要有 mockup）

- **空态**：存档为空 / 草稿为空（友好插画或图标 + 文案，**不要显示裸 "0"**）
- **加载态**：首次拉取时
- **错误态**：同步/读取失败
- **同步中**：后台 worker 同步时的轻量指示（可选）+ 手动「同步」按钮的 pending 态
- **操作 pending**：发送/删除/移回 进行中（按钮 loading）

## 7. 约束与边界

- **平台**：桌面 Electron 窗口，最小宽度约 1000px（自适应密度：宽屏显 toolbar 文字 label，窄屏仅图标）
- **发送合规提示**：发送走 DavMail（当前 PoC 模式），UI 上发送必须二次确认；措辞可中性（"确认发送给 N 位收件人？"）
- **i18n**：中文为主（项目已有 zh-CN/en-US，文案走 i18n key）
- **不在本次范围**（设计可忽略 / 标注为后续）：
  - 附件**二进制下载/预览**（当前只展示元数据，点击不下载）
  - 正文内嵌图片（cid:）渲染
  - 富文本编辑器的字号/字体颜色/引用块/表格等高级格式（先做基础格式集）

## 8. 当前工程实现现状（基线，供设计参考与改进，不必沿用）

已有一版可运行实现（`frontend/src/shared/components/folder/`），结构：
- `FolderLayout`：两栏壳（列表列 340px + 详情列 flex）
- `FolderList` / `FolderRow`：列表（顶部标题 + 同步按钮 + 草稿的新建按钮 + 计数）
- `FolderDetail` + `FolderToolbar`：详情 + 操作栏（按存档/草稿分叉）
- `DraftEditor`：撰写器（收件人行 + TipTap 正文 + 格式工具栏）
- `ConfirmDialog`：二次确认弹窗
- `FolderBodyFrame`：正文 iframe

**已知可改进方向**（设计可重新考虑）：列表行的信息层次与密度、详情页的留白与元数据呈现、
撰写器的编辑体验与工具栏布局、空/加载态的精致度、操作按钮的视觉权重与确认流。

## 9. 给设计师的交付建议

- **形式**：mockup HTML（与 `frontend/ref/mockup-*.html` 同风格，含真实 ink token 的 CSS），
  或分屏静态稿。覆盖下列屏 × 态：
  1. 存档 — 列表（有数据 / 空）+ 选中某封的详情
  2. 草稿箱 — 列表（有数据 / 空）+ 详情
  3. 撰写器 — 新建（空）+ 编辑（载入草稿）
  4. 三个确认弹窗（移回 / 删除 / 发送）
  5. 加载态 / 错误态
- **重点**：与收件箱视觉连续性 + 存档/草稿因「无 AI 信息条、无线程」而能更干净的版面 + 撰写器体验。
- 标注清楚用到的 token / 字号 / 间距，方便工程 1:1 还原。
